# Noise VPN: project guide

Handoff notes for continuing this project in a new chat. Upload this file together with a zip of the project (without `build/`, `.dart_tool/`, Pods and the `windows/xray` binaries) so the code can be read before changing anything.

## What it is

A free Flutter VPN client called **Noise VPN** built on **flutter_vless 1.1.7** (Xray core 26.10.31). There is no login: the app opens straight to Home. It has a Home screen with connect/disconnect, a Servers screen and Settings. Its look is modelled on the owner's admin panel **Palgam**: dark, rounded cards, violet sidebar glow, 12 accent colours, light/dark/system. Only the look is shared; the client is a separate product.

The owner writes in casual Persian. The UI ships in Persian and English.

## Working rules learned so far

- **No fake data, ever.** Nothing may be simulated in the app: no fake connections, no fake pings or speeds. Where something can't work (Linux, web), the UI says so and disables it.
- **Real ping only.** A ping number must mean a real request went through that server's config. A TCP handshake is not acceptable, because it only shows the port is open.
- **Ping must be fast and parallel, like v2rayNG / Happ.** Sequential one-by-one testing was rejected as slow and unappealing.
- **No country grouping.** Every config is its own row. Grouping by source (subscription / local configs) is fine.
- **Layout never mirrors.** It stays left-to-right in both languages; only the text changes. Persian strings are wrapped with `rtl()` so punctuation and word order stay right inside each string.
- **Performance matters.** Per-card `BackdropFilter` blur dropped the app to about 30 fps on a phone and was removed. "Glass" now means translucent fill plus a sheen, with no blur. Avoid `BackdropFilter` inside lists and scroll views.
- **No login.** The owner removed it to publish the app for free; `lib/features/auth/` is deleted.
- **Deliver zips of changed files.** The owner unzips them into the project. When a file is deleted, say so explicitly: stale files once broke the build (`simulated_vpn_backend.dart`). When many files change, offer the full `lib/` and tell them to delete the old folder first.
- **The code can be statically analyzed in Claude's sandbox**, though not built. pub.dev and storage.googleapis.com are blocked, but this works: the Dart SDK from conda-forge (`dart-sdk`), Flutter framework sources from a sparse clone of `github.com/flutter/flutter` (`packages/flutter`, `packages/flutter_localizations`, `engine/src/flutter/lib/ui`), a hand-made `sky_engine` whose `_embedder.yaml` maps `dart:ui` to `lib/ui/ui.dart`, and every dependency cloned from GitHub (riverpod at tag `flutter_riverpod-v2.6.1`, flutter/packages, dart-lang/core, dart-lang/tools, dart-lang/http, flutter_vless tag `v1.1.7`). A hand-written `.dart_tool/package_config.json` ties them together, then `dart analyze lib`. Pure-Dart files (WireGuard parser, config tweaks) can also be run against flutter_vless's own `XrayConfigValidator`. The SDK needs a `version` file in its root.

**Auto-update:** each subscription has a schedule (Off, As the subscription says, every 6/12/24 h, custom 1–168 h), set when adding it or from the pencil button on its section. "As the subscription says" follows the `profile-update-interval` header and falls back to the chosen hours (12 by default); intervals are clamped to at least 15 minutes. `ServersController` refreshes due subscriptions at launch, every 5 minutes while the app is open and on resume; a failed attempt isn't retried automatically for 15 minutes. Nothing runs in the background on phones. Editing the link drops the cached copy and downloads again; refreshes for an old link are discarded.

The subscription request sends `User-Agent: NoiseVPN/<version>`. A failed or empty refresh keeps the cached servers and marks the source `failed`.

**Plan card on Home:** it shows the subscription of the server in use: the connected one, otherwise the selected one (or the fastest in auto mode). With several subscriptions it follows the selection and names the subscription. It's hidden for local configs and for subscriptions without a `subscription-userinfo` header.

**Home layout on phones (and narrow tablets):** fixed, no scrolling. In order: title, optional notice, connect panel taking the remaining height (the button sizes itself to it), location card, a one-row stats strip, a compact plan card. Below 540 px of height (620 with the plan card) it falls back to a scroll view. Desktop keeps the two-column layout.

## Ping

Ping **never runs by itself**: not on launch, and not after adding or refreshing a source. The owner asked for this. Two things start it:
- **Test ping** in the Servers header: all servers.
- **A row's ping badge** (`PingController.testOne`): just that server. The badge shows a speed icon when the server was never tested. The Home location card's badge works the same way.

The last result of every server is saved (`ping.results`) and shown again on the next launch.

### Main path: parallel, like v2rayNG

`batch_ping_io.dart` starts **one** Xray process with a SOCKS inbound per server (`in<i>` on a free loopback port) routed to that server's proxy outbound (`p<i>`). All servers are probed at once, up to 16 concurrent. Each probe does a SOCKS5 CONNECT to `www.gstatic.com:80` plus `HEAD /generate_204`, timed until a valid status line arrives. Timeout is 5 s per server, and results appear as they finish.

Where the Xray binary comes from:
- **Android:** `<nativeLibraryDir>/libxray.so`, the file flutter_vless already ships. The path comes from the `noisevpn/native` channel in `MainActivity`.
- **Windows:** `xray/xray.exe` next to the app.
- **Linux:** `xray` next to the app, in `xray/`, or on PATH.
- **iOS / macOS:** not possible (sandbox).

### Fallback: flutter_vless `getServerDelay`

This is the plugin's own probe, used sequentially with a 5 s timeout and a drain wait. It's slow because the Android plugin:
- runs probes on a single-thread executor,
- starts a new Xray process per probe,
- copies geoip/geosite to disk every time.

The fallback runs when the batch engine can't start. If every batch probe failed, it first checks whether the plugin can reach one server.

**Status:** the batch engine was delivered but **not yet confirmed on a device**. If every ping times out, look at `adb logcat | grep -iE "flutter|xray batch"`.

- **macOS:** run `dart run flutter_vless:setup_macos_vpn --bundle-id com.noise.vpn.noisevpn --group-id group.com.noise.vpn.noisevpn --team-id …` on a Mac (see README). Not done yet.
- **iOS:** `Runner.entitlements` (Network Extension + App Group) is wired into all three Runner configs, and `FlutterVlessKeychainAccessGroup` is in Info.plist. The `XrayTunnel` target still has to be created in Xcode; its files are in `ios/XrayTunnel_template/` (provider copied from the flutter_vless 1.1.7 example). Steps in README. iOS rejects `bypassSubnets` in VPN mode, so Bypass LAN becomes Xray direct rules there.
- **Geo data:** Android and Windows ship geoip.dat / geosite.dat (they contain `geosite:category-ir`, `geoip:ir`, `geosite:category-ads-all`). The Apple runtimes ship none, so Apple gets only the `regexp:\.ir$` rule and no ad blocking.
- **Linux:** no VPN engine in flutter_vless, so Connect is disabled with a notice. Server list is real. Ping works only if an `xray` binary is present.

## Keeping the connection state honest

On Android, flutter_vless runs `XrayVPNService` in a **separate process** (`:RunSoLibXrayDaemon`) and reports state only through broadcasts. Those can be missed: the process can die, the receiver may be unregistered, or Android may queue broadcasts for background apps. That led to "app says connected, VPN is off". So `VpnController`:
- calls `ensureInitialized()` at launch (the status listener used to start only on the first Connect),
- calls `verify()` on launch, on app resume (`AppLifecycleListener`), and when no status has arrived for 6 s while not disconnected,
- `verify()` asks `backend.isSessionAlive()`. On Android that's the `vpnServiceRunning` channel method (`ActivityManager.getRunningServices`); other platforms return null, meaning "can't tell, trust the stream",
- if the service is gone, the app shows disconnected. If it's running while the app thinks it's off, the app shows connected with the last server (`vpn.lastServerId`),
- skips checks for 10 s after the user's own connect or disconnect.

## VPN options flutter_vless exposes (all wired in Settings)

- `startVless(proxyOnly)`: no VPN, a local SOCKS5 on the config's socks inbound. The default port is 8142; we rewrite the inbound port to the chosen one.
- `blockedApps`: Android only, excluded from the tunnel.
- `bypassSubnets`: we pass the LAN ranges when Bypass LAN is on.
- `androidDnsPolicy`: `proxy` when "DNS through the tunnel" is on, `config` otherwise and in proxy mode.
- **Windows** (from `doc/platform/windows.md`; 1.1.7 captures IPv4 and IPv6 in the tunnel):
  - proxy-only sets `socks=127.0.0.1:<port>` as the Windows system proxy and restores it on stop,
  - VPN mode is a Wintun TUN and needs administrator,
  - DNS always goes through the proxy,
  - IPv4 `bypassSubnets` become direct rules in Xray (so Bypass LAN is shown on Windows),
  - `blockedApps` and the DNS policy are Android-only,
  - runtime files must sit in `xray/` next to the exe (PATH isn't searched),
  - after a crash the WFP block stays until the app is reopened as admin and stopped.
- 1.1.7 engine options (`VlessOptions`, given to the `FlutterVless` constructor): notification button/action, quick access (tile / menu bar / tray / Control Center), reconnect backoff, protection (kill switch is always on; On Demand; Android Always-on requirement), diagnostics. A changed option needs a new `FlutterVless` instance + `initializeVless`. On Apple, stop the tunnel first.
- Routing rules, DNS and fragment are edits to the Xray JSON (`config_tweaks.dart`).

## Answered questions

- **WireGuard:** now supported (owner's request), via `wireguard.dart`. Caveat still true: the handshake is easy for DPI to block on filtered networks.
  Background: Xray core runs WireGuard outbounds, and flutter_vless 1.1.6 already builds them, but only from Clash or sing-box subscriptions (`subscription.dart`). It has no parser for `wireguard://` links or `.conf` files. Adding our own parser that produces the same `{"protocol": "wireguard", ...}` outbound is possible.
  - Caveat: it's Xray's userspace WireGuard behind tun2socks, slower than the official app.
  - Caveat: the WireGuard handshake is easy for DPI to detect and block on filtered networks.
